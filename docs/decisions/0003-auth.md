# ADR 0003: Staff sign-in, sessions and permissions (Phase 1)

Status: accepted 2026-11-17. The proposal (`Plan/Phase1-Design-Proposal.md`) was approved as written, recommendations included.

## Decisions

- **Identity.** ASP.NET Core Identity *core* (`AddIdentityCore`) for password hashing, lockout and security stamps, over our own `Domain.Identity.User` entity via `Infrastructure/Identity/UserStore`. No `IdentityDbContext`, Identity UI or Identity cookies. This keeps the Domain project free of packages (architecture test) and gives every auth table the normal audit columns and soft-delete filter. There is no `RoleManager`; roles are plain entities.
- **Login.** Email (case-insensitive, unique among non-deleted users). Staff only (`UserType.Staff`); customers arrive in Phase 6.
- **Access token.** HS256 JWT, 10 minutes, claims `sub`, `sid` (sign-in family), `stamp` (16-char hash of the security stamp), `jti`. Issuer, audience, signature, lifetime and algorithm validated, 30 s skew. `Jwt:SigningKey` (≥ 32 bytes) is required outside Development/Testing; Development without one uses a random per-process key, so sign-ins end on restart. Permissions are **not** in the token.
- **Refresh token.** 32 random bytes, stored only as SHA-256 hex. Cookie `sp_refresh`: HttpOnly, Secure, SameSite=Strict, Path=/api/auth. 14 days sliding, 30 days per sign-in at most.
- **Rotation and replay.** A refresh consumes the token with one conditional `UPDATE … WHERE ConsumedAt IS NULL AND RevokedAt IS NULL` and inserts the replacement in the same transaction; of two simultaneous refreshes only one wins (the other gets 409 and retries). Reuse of a consumed token within 5 s returns 409; after that it is treated as theft and revokes the whole family (`TokenReplay` security event). The admin app serialises refreshes across tabs with the Web Locks API and shares one refresh within a tab.
- **CSRF.** Refresh and logout require an `Origin` in `Cors:Origins` and the header `X-CSRF-Token: 1` (forces a preflight), on top of SameSite=Strict. **Admin app and API must share a registrable domain in production** (e.g. `admin.` and `api.` of the shop domain); otherwise this needs revisiting.
- **Permissions.** Stable keys in `Application/Identity/PermissionKeys` (each is also a policy name). Roles hold keys; users can have Allow/Deny overrides; effective = roles ∪ Allow − Deny, **Deny wins**, no role inheritance, SuperAdmin has every key and cannot be denied. Keys for Phases 3–6 (inventory, sales, delivery, refunds) exist now.
- **One override table (D8).** The spec's `UserMenuPermission` is implemented as `user_permission_overrides`; each menu needs one permission key, so the menu screen and the API can never disagree. Hidden menu ⇒ its API returns 403.
- **When changes apply.** Access is resolved per request from a 15-second memory cache (`AccessService`); changes on the same server clear it at once, other servers within 15 s. The `PermissionVersion` column from the proposal was dropped as unnecessary. Password change/reset, deactivation, deletion, sign-out-everywhere and SuperAdmin removal revoke all refresh tokens and change the security stamp, so access tokens stop within the same window.
- **Roles.** System roles SuperAdmin, Admin, StoreKeeper, Cashier, seeded with default permissions only when first created. System roles cannot be renamed or deleted; SuperAdmin's permissions cannot be edited. Custom roles can be deleted only when unassigned.
- **SuperAdmin.** Only a SuperAdmin can create, edit, reset, delete or (un)assign SuperAdmins. Removing the last active SuperAdmin (deactivate, delete, role removal) returns 409, checked under `pg_advisory_xact_lock(7340001)` so two concurrent attempts cannot both succeed. Users cannot deactivate or delete themselves.
- **Bootstrap.** No seeded password. `tools/AdminBootstrap` creates the first SuperAdmin (password from `BOOTSTRAP_PASSWORD` or a hidden prompt) and refuses when an active SuperAdmin exists. Audit actor `system:bootstrap`.
- **Seeding.** Roles and menus are synced from code by `IdentitySeedService` at API start (background, non-fatal) and by the bootstrap tool. Menus for later phases are seeded disabled. Refresh tokens whose sign-in ended more than 60 days ago are purged at start.
- **Login protection.** Lockout after 5 failures for 15 minutes; 10 login requests per minute per IP (429) and 5 per minute per email per server. Unknown email, wrong password, inactive and locked accounts all get the same 401 "Email or password is incorrect."; unknown emails still run a hash check. Password: 12+ characters, no composition rules, not the email. Admin-set passwords force a change at next sign-in.
- **Refunds (D15).** `refunds.create` (Cashier, Admin), `refunds.approve` and `refunds.execute` (Admin). The "cannot approve your own refund" rule is for Phase 4.
- **Deleted records.** `includeDeleted` on catalogue lists needs `catalog.deleted.view`; on users, `users.manage`.
- **Audit.** Join rows (user roles, role permissions, overrides) use a Guid key plus a unique index rather than a composite key, to share the audit base class. Refresh-token consume/revoke updates set `UpdatedAt/UpdatedBy` explicitly because they bypass the interceptor.

## Open items

- Production domains for the admin app and API (same registrable domain assumed).
- PostgreSQL auth tests (rotation race, replay, lockout, last-SuperAdmin race) need a disposable database; not yet run.
- The `Phase1Auth` migration has not been applied to the hosted database.
- Per-email login throttling is per server; lockout is the cross-server guard.
